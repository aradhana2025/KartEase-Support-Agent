# KartEase RAG Customer Support Agent

## 1. Project Overview

KartEase is an AI-powered customer support assistant designed to answer questions about e-commerce policies and retrieve customer order information.

The system combines Retrieval-Augmented Generation (RAG), a vector database, a Large Language Model (LLM), and a CSV-based order lookup tool.

The application uses policy documents as its knowledge base and retrieves relevant information to answer customer questions. It also provides order details using an order ID.

## 2. Features

- Search policy documents using semantic similarity.
- Answer questions about returns and refunds.
- Retrieve shipping, delivery, warranty, and repair information.
- Look up customer orders using order IDs.
- Handle invalid order IDs with a friendly message.
- Use an AI agent to select the appropriate tool.
- Support requests that require policy information and order details.
- Provide a predefined fallback response for recognized unrelated questions.
- Store policy embeddings persistently in ChromaDB.
- Include automated tests for order lookup and policy retrieval.

## 5. Setup and Installation

### Prerequisites

- Python installed on the system.
- A Google Gemini API key.
- Visual Studio Code or another Python editor.
- Internet connectivity for API requests.

### Step 1: Open the project directory

Open a terminal in the `kartease_starter` directory.

All commands in this README should be executed from this directory unless otherwise specified.

### Step 2: Create a virtual environment

On Windows PowerShell, run:

```powershell
python -m venv .venv
```

Activate the virtual environment:

```powershell
.\.venv\Scripts\Activate.ps1
```

If the virtual environment is already active, skip these commands.

### Step 3: Install dependencies

Run:

```powershell
python -m pip install -r requirements-langchain.txt
```

### Step 4: Configure environment variables

Create a `.env` file in the project directory using `.env.example` as a reference.

Add your Gemini API key using the environment variable name expected by the project.

Never share the API key publicly or upload the `.env` file to GitHub.

### Step 5: Build the knowledge base

Run:

```powershell
python build_knowledge_base.py
```

The script:

1. Loads the policy documents from the `data/` directory.
2. Splits the documents into smaller text chunks.
3. Generates embeddings for the chunks.
4. Stores the embeddings and associated document metadata in ChromaDB.
5. Reuses the existing knowledge base when vectors are already present.

The current implementation reuses an existing database rather than automatically refreshing it when policy documents change. If the policies are modified, rebuild the database using the appropriate database-reset procedure before running the builder again.

## 6. Running the Application

Run these commands from the project directory.

### 6.1 Search policy documents

Run:

```powershell
python search_policies.py
```

Enter a policy question when prompted.

Example:

```text
How many days do I have to return a phone?
```

The program retrieves relevant policy chunks and displays their source filenames.

This component tests semantic retrieval independently of LLM answer generation.

### 6.2 Generate an answer using RAG

Run:

```powershell
python answer_policies.py
```

Example question:

```text
How many days do I have to return a phone?
```

The system retrieves relevant policy information, sends the context to Gemini, and generates an answer with source filenames.

The answer must be based on the supplied policy information.

If the question is unsupported or unrelated, the required fallback response is:

```text
Sorry, I can only help with KartEase orders and policies.
```

Clearly unrelated questions included in the current rule list can return the fallback without invoking Gemini's generation model.

### 6.3 Look up an order

Run:

```powershell
python order_lookup.py
```

Enter an order ID when prompted.

Example:

```text
KE1002
```

The program displays the available order information, including:

- Order ID
- Customer name
- Product
- Category
- Order date
- Order status
- Expected or delivered date
- Amount
- Payment method

For an unknown order ID, the application displays a friendly message.

Example:

```text
Sorry, no order was found with ID KE9999.
```

### 6.4 Run the AI customer support agent

Run:

```powershell
python kartease_agent.py
```

Example questions include:

```text
Where is my order KE1002?
```

```text
What is the return policy for electronics?
```

```text
How are refunds processed?
```

```text
Check order KE9999.
```

The agent uses the Gemini model to select the appropriate tool for the customer's request.

The available tools are:

- `search_policy`: Retrieves policy information and generates a policy-based answer.
- `check_order`: Retrieves order information from `orders.csv`.

The agent is designed to use both tools when a request requires policy information and order details.

The application displays the tool names used during processing.

Enter `exit` or `quit` to leave the interactive application.

**API quota note:** Agent tool selection and policy answer generation depend on Gemini generation requests. If the API quota is exhausted, these operations may fail until the quota becomes available again.

## 9. Attempted Fix

### Problem

The application initially attempted to invoke Gemini for clearly unrelated questions, even when the required fallback response could be returned directly.

This used generation requests unnecessarily.

### Fix implemented

A rule-based check was added to `answer_policies.py` to recognize specific unrelated questions before calling Gemini.

The agent was also updated to use this check before invoking its language model.

### Verification

The following question was tested:

```text
Who is the CEO of Google?
```

The application returned the required fallback response without calling Gemini's generation model.

**Result: PASS for the tested question.**

### Remaining limitation

The rule-based check currently handles only explicitly listed question patterns. It does not guarantee that every possible unrelated question or unsupported policy question will receive the fallback response.

A more comprehensive relevance-classification approach and further testing are needed.

## 10. How the System Works

The KartEase application follows these steps.

1. Policy documents are loaded from the `data/` directory.
2. Each document is split into smaller text chunks.
3. Google Generative AI Embeddings converts the chunks into vector representations.
4. ChromaDB stores the vectors and associated metadata persistently.
5. A customer submits a policy question, an order query, or a combination of both.
6. The Gemini-powered agent selects the relevant tool.
7. Policy questions retrieve relevant document chunks and use Gemini to generate a grounded response.
8. Order queries retrieve matching records from `orders.csv`.
9. The application returns the result, including policy source filenames or tool usage where applicable.

## 11. Limitations

### 11.1 Local order data

Order information is stored in a local CSV file rather than a live e-commerce order management system.

As a result, the application cannot retrieve real-time updates from an external order service.

### 11.2 Gemini API quota dependency

Policy answer generation and agent tool selection depend on the Gemini generation API.

If the configured API quota is exhausted, generation and tool selection may fail until the quota becomes available again.

The current rule-based fallback also recognizes only specific unrelated-question patterns.

Additional limitations include the following:

- Policy answers depend on the available documents and retrieved context.
- The knowledge-base builder reuses existing vectors and does not automatically refresh changed policy documents.
- The application is a prototype rather than a production customer support platform.

## 13. Security

- Store API keys in environment variables.
- Never commit `.env` or expose API keys.
